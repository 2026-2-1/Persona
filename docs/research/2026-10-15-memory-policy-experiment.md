# 메모리 검색 정책 실험 준비 — 2026-10-15

후속 팀 대화의 성찰·계획 검토 off/빈도 비교는 [상위 실험 계획](2026-10-15-slow-loop-experiment-plan.md)에 반영했다. 이 문서는 그 계획의 **2차 메모리 검색 실험 상세 근거**로 사용한다. 아래 Slow 주기 고정은 검색 정책을 비교할 때의 조건이며, 1차 빈도 실험에서 주기를 고정한다는 뜻이 아니다. 기업체 데이터는 사용자 확인 기준 미수령 0건이다.

## 결론과 범위

활성 기억의 상한은 64개로 고정하고, **Fast/Slow 검색 가중치가 웹 과업 성공·반복 행동·시간·비용에 미치는 영향**을 한 가지 연구 질문으로 삼는 방향을 제안한다. 검색 정책을 실제 모델 입력에 연결한 뒤, 같은 과업·페르소나·모델·예산에서 조건을 대응 비교한다. 여기의 숫자와 표본 규모는 실험 초안이며 팀의 확정 결정이나 검증 결과가 아니다.

이 문서는 논문 원문과 공개 PR 코드를 읽은 준비 자료다. 유료 API, 실제 모델 실험, 인간 참가자 실험을 수행하지 않았다. 현재 확인한 PR은 모두 미병합이므로 아래 구현 상태를 `prototype` 완료 상태로 해석하지 않는다. 실험에서 성능 차이를 확인해도 사람 행동·판단을 재현한다는 근거는 별도로 필요하다.

## 논문에서 확인되는 내용

UXAgent는 중요도·관련성·최신성과 기억 종류 가중치를 조합한다. Fast는 최신성, Slow는 관련성을 강조한다. 중요도는 Slow에서 비동기로 산정하며 미산정 값은 검색 계산에서 제외한다. 관련성은 임베딩 유사도, 최신성은 생성 시각에 대한 지수 감소다. Appendix C.7은 기억·페르소나·의도·현재 계획을 주고 중요도를 1~10으로 평가하도록 한다. 이 설명에서 **Slow의 중요도 우선 검색이나 활성 64개를 논문의 정답 설정으로 도출할 수 없다.** [UXAgent v3 §3.2](https://arxiv.org/html/2504.09407v3#S3.SS2), [Appendix C.7](https://arxiv.org/html/2504.09407v3#A3.SS7)

논문 방향의 가중치 조건은 비교 대상으로 삼되, 아래 정확한 계수는 프로젝트가 선택한 가설로 기록한다. 논문의 감소율 `k=1`도 시간 단위와 구현을 확인하지 않고 우리 코드의 초 단위에 그대로 복사하지 않는다.

## 실험 시작을 막는 구현 선행 조건

1. **Slow의 검색 소비 경로를 확인한다.** 확인한 PR #53/#63 계열의 `SlowLoop`는 활성 목록 snapshot 전체를 성찰 입력으로 전달한다. `MemoryStore.retrieve(mode="slow")`를 호출하는 정책 비교 경로가 아니다. `mode` 인자는 #53에서 가중치 계산에 쓰이지 않는다. 설정 이름만 바꾸고 Slow 가중치 효과를 측정했다고 주장할 수 없다. [Slow snapshot](https://github.com/2026-2-1/Persona/blob/825206294274f8dba883d97764d2ad6087a95ec4/src/uxagent/slow_loop.py), [동일 가중치 검색](https://github.com/2026-2-1/Persona/blob/825206294274f8dba883d97764d2ad6087a95ec4/src/uxagent/memory.py#L89)
2. **별도의 메모리 정책 실험 실행 경로가 필요하다.** 확인한 #63의 기존 `run_comparison`은 일반/페르소나 비교이며 Slow 활성 설정을 거절한다. 기존 조건 이름만 재활용하면 페르소나 효과와 메모리 효과가 섞인다. 일반/페르소나 비교의 계약은 유지하고 `memory_policy_id` 조건을 분리한다. [기존 비교 실행기](https://github.com/2026-2-1/Persona/blob/2c5f72ad0366b406193f1b382006927ce24c5dbe/src/uxagent/experiments.py#L16)
3. **정책이 실제로 입력을 바꾸는지 검사한다.** 순위 상위 기억, 실제 전달 기억, 단계별 출처 ID를 대조한다. 필수 현재 관찰·의도·구매 제약·현재 계획은 top-k와 별도 문맥으로 고정한다. 다른 provider/fallback의 4/6개 차이를 조건 차이로 섞지 않는다. [#54 완료 조건](https://github.com/2026-2-1/Persona/issues/54), [#63 단계 기록](https://github.com/2026-2-1/Persona/blob/2c5f72ad0366b406193f1b382006927ce24c5dbe/src/uxagent/runner.py#L145)
4. **비동기·제거 경계를 fake provider로 먼저 검사한다.** 늦은 중요도 도착, 이미 제거된 ID, 취소, 상한 10/64, 오래된 snapshot 출처를 확인하고 원본 로그를 보존한다. 단위 검증이 통과해도 실제 모델 성능을 검증한 것으로 쓰지 않는다. [#55](https://github.com/2026-2-1/Persona/issues/55), [#56](https://github.com/2026-2-1/Persona/issues/56)

별도로 원격 `feat/42-slow-reflection-review` 브랜치의 작업도 있으므로, 통합 직전에는 실제 채택 commit과 Slow 입력 경로를 다시 확인한다. 이 문서의 PR 코드 판단은 위 고정 head에 한정한다. 아직 검토·통합되지 않은 팀원 브랜치가 `prototype`에 적용됐다고 가정하지 않는다.

## 제안하는 3개 조건

가중치 순서는 **(중요도 I, 관련성 Q, 최신성 R)** 이다. 전 요소가 유효할 때의 계수이며, 미산정 값의 처리와 동점 규칙도 모든 조건에서 동일하게 고정한다.

| 조건 ID | Fast | Slow | 비교하려는 내용 |
|---|---|---|---|
| `equal-v1` | (1/3, 1/3, 1/3) | (1/3, 1/3, 1/3) | #40 동일 가중치 기준선 |
| `fast-recent-slow-relevant-v1` | (0.2, 0.3, 0.5) | (0.2, 0.5, 0.3) | 논문 설명에서 방향을 얻은 팀의 구체적 정책 |
| `fast-recent-slow-important-v1` | (0.2, 0.3, 0.5) | (0.5, 0.2, 0.3) | Slow 중요도 우선이라는 팀 가설 |

두 번째와 세 번째 조건은 Fast와 Slow 최신성 계수를 같게 두고 Slow의 I/Q 배분만 바꾼다. 이를 **주 비교**로 사전 지정하면 Slow의 중요도/관련성 강조 효과를 더 직접적으로 볼 수 있다. 첫 번째와 두 번째 조건은 Fast와 Slow가 함께 변하므로 전체 검색 정책 차이를 보는 보조 비교다. Fast만의 효과까지 분리하려면 후속으로 Fast 가중치를 고정한 대조 조건을 추가한다.

가중치 정규화·미산정 제외·동점 최신순·기억 종류 가중치·중복 제거를 명세한다. 논문에 있는 기억 종류 가중치를 새로 넣는다면 모든 조건에 동일하게 적용하고 기존 코드와의 차이를 기록한다. 가중치와 최신성 감소율, embedding 모델을 한 번에 바꾸지 않는다.

## 고정할 변수와 비동기 조건

- **환경:** 같은 로컬 fixture commit, 상품·가격·재고 데이터, 초기 URL, viewport, 브라우저 버전, 네트워크 조건. 세션별 새 context와 저장 상태 초기화를 사용한다. 실제 사이트 결과는 별도 묶음으로 기록한다.
- **입력:** 같은 과업·구매 제약·페르소나 파일·prompt version·평가기. 실험 전체에서 persona 모드를 고정하고 일반 AI 효과를 동시에 비교하지 않는다.
- **모델:** provider와 정확한 모델명·temperature·최대 출력 토큰·fallback 정책을 고정한다. 초기 실험은 한 생성 provider를 제안한다. Jev/fallback 실험은 별도로 두어 실효 기억 수와 모델 전환 영향을 구분한다.
- **메모리:** 활성 상한 64, 최근 10개 보호, 제거 규칙, 중요도 모델/프롬프트/동시성, 검색 질의, Fast/Slow 실효 top-k를 고정한다. 초안으로 생성 모델의 실효 top-k는 양쪽 모두 6을 제안하지만, Slow 소비 구현 후 가능 여부를 확인해 확정한다. `memory_limit=8`을 유지하면 실효 6개로 자른다는 사실도 명세한다.
- **시간:** 우선 현재 반감기 60초를 유지한다. replay는 기록 당시의 시각을 고정하고, live에서는 실제 경과 시간을 기록한다. 시간 단위·clock 종류·동점 규칙을 버전으로 남긴다.
- **Slow:** 켜짐, 발동 주기, 오류 발동, wonder 켜짐 여부를 같게 둔다. 초기에는 wonder를 끄는 안을 제안한다. 중요도 산정과 성찰의 호출·대기·취소를 구분한다.
- **예산:** 모든 조건에서 같은 양의 요청·토큰 상한, 최대 단계·실행 시간·요청별 출력 상한을 명시한다. 무제한 기본값에 맡기지 않는다. 파일럿의 실측 사용량으로 상한을 정한 뒤 평가 구간에서는 바꾸지 않는다.

PR #53은 요청/총토큰 기본값을 `null`로 바꾸고 양의 제한을 계속 지원한다. 중요도 작업은 별도 LLM 요청을 소비한다. PR #63은 Fast 생성 단계를 3회로 분리하고 관찰·인식·계획·행동 기억 4개에 점수 작업을 예약하므로, 이전 단일 생성/행동 비용 예상치를 그대로 사용할 수 없다. repair·embedding·fallback·성찰도 총 사용량에 포함해야 한다. **예약 가능한 최대 요청 수와 실제 수행 요청 수는 다르다.** [#53 설정](https://github.com/2026-2-1/Persona/blob/825206294274f8dba883d97764d2ad6087a95ec4/src/uxagent/schemas.py#L54), [#63 호출과 중요도 예약](https://github.com/2026-2-1/Persona/blob/2c5f72ad0366b406193f1b382006927ce24c5dbe/src/uxagent/runner.py#L145)

비동기는 같게 설정해도 모델 응답 시간 때문에 점수 반영 시점이 달라질 수 있다. `scheduled/started/completed/skipped/failed/cancelled`, 당시 snapshot 순번과 점수 도착 시각을 남긴다. 검색 시점의 **점수 산정 완료율·대기 수·점수 작업 취소율**을 보조 지표로 보고한다. live에서 결과를 결정적으로 보이게 만들려고 Fast를 기다리게 하면 비동기 구조 자체가 바뀌므로 별도 실험 조건으로 취급한다.

## 두 단계 검증: offline replay와 live rollout

### 1. Offline replay — 검색 정책이 의도대로 다른 기억을 고르는가

기록된 검색 시점마다 당시 활성 기억·당시 점수·질의·시각·snapshot을 복원하고 세 정책을 재계산한다. 그 시점 이후 도착한 중요도나 미래 행동의 근거를 넣으면 정보 누출이다. 로그에 당시 질의·시각·변경 순서가 없으면 완전 재현이라고 하지 않고 “고정 snapshot에서의 순위 분석”으로 범위를 낮춘다.

정책별 top-k ID/순서, 겹침 비율, 기억 나이·종류·중요도 분포, 과업 관련 기억의 포함 여부를 분석한다. 과업 관련성을 사람이 주석하면 조건을 가린 독립 판정과 불일치 처리를 기록한다. 기본 토큰 겹침과 embedding 유사도를 섞어 동일 정책으로 집계하지 않는다.

이 분석은 기존 행동을 바꾸지 않으므로 **새 정책의 성공률 개선이나 호출 비용 절감을 입증하지 않는다.** 검색 코드·출처·실제 입력 개수의 회귀를 API 비용 없이 먼저 확인하는 용도다.

### 2. Live rollout — 정책을 바꿔 실제로 다시 행동하게 한다

같은 과업·페르소나·반복 블록에서 정책마다 브라우저와 기억을 초기화해 새 실행을 한다. 여기서 live rollout은 모델의 새 결정이 환경에 반영된다는 뜻이며, 초기에는 로컬 fixture에서 수행할 수 있다. 실제 서비스 사이트를 명시적으로 설정한 기록의 `source_kind=live_configured`와 구분한다.

정책 순서는 블록별로 균형 있게 섞고 seed·실제 순서를 저장한다. 모델이 seed를 지원하지 않으면 요청 순서 seed가 모델 응답의 완전 재현성을 보장한다고 쓰지 않는다. 비동기 완료 순서·provider 버전·실행 시각을 함께 남긴다. 실제 사이트는 내용 변화가 있으므로 가까운 시각의 대응 블록과 관찰된 사이트 상태를 기록하고 fixture 결과와 합치지 않는다.

## 지표와 분모

주 지표는 **독립 과업 성공률**로 사전 지정한다. 나머지는 성능 차이의 원인·비용·불확실성을 설명하는 보조 지표다. 모델의 완료 선언, 사람의 후보 유효 판정, 독립 과업 성공을 같은 값으로 합치지 않는다. 기존 [평가·기록·결과 계약](../contracts.md)을 따른다.

| 지표 | 정의와 보고 방법 | 해석 주의 |
|---|---|---|
| 독립 성공률 | 독립 평가기 `success` / 사전 등록 세션 수. 실패·unknown·error·blocked·cancelled·not_started 개수도 공개한다. | 평가 실패와 실행 오류는 별도 축이다. 분모에서 실패/중단을 제거하지 않는다. |
| 불필요 반복 | 같은 행동 입력이 같은 관찰 상태에서 반복되는 비진행 사건 수와 해당 세션 비율. 정상 polling·의도된 반복·복구 행동 제외 규칙을 사전 정의한다. | 기존 `stuck` 종료는 참고 신호다. 모든 반복이 UX 문제이거나 기억 실패인 것은 아니다. |
| 행동 수 | 전체 세션의 시도 수 분포, 성공 세션의 행동 수 중앙값과 대상 수를 함께 표시한다. | 성공 세션만 빨라져도 전체 성공률이 낮아질 수 있다. |
| 실행 시간 | 시작~종료 wall time, 성공 세션 중앙값/대상 수, 전체 종료 시간 분포. | 병렬 LLM 호출 시간의 합은 wall time과 다르다. |
| 요청·토큰·비용 | Fast·중요도·성찰·embedding·repair·fallback별 요청/실측 입력·출력 토큰, 가격 확인 가능한 추정비용. 전체/부분 측정과 누락 호출·세션 수를 공개한다. | 예산 예약 토큰을 실측으로 쓰지 않는다. 누락은 0으로 바꾸지 않고 비용 산식·가격 기준일을 남긴다. |
| 예산 중단 | `budget_exceeded` 세션 수 / 예정 세션 수. 시간·단계·반복 제한 종료는 각각 별도 표시한다. | 상한에 걸린 비율도 정책의 결과다. 빠진 세션처럼 삭제하지 않는다. |
| 메모리 소비·출처 | 검색 top-k 대비 실제 입력 ID 일치, snapshot/원본/변경 사건 추적 가능 비율, 점수 산정 완료율·취소율. | 입력에 존재하는 것과 모델이 그 기억 때문에 행동했다는 인과 설명은 다르다. |

초기 불필요 반복 규칙은 “동일한 정규화 행동+동일한 상태 지문에서 반복된 추가 시도”로 정하고, 검토용 사건 목록을 남기는 안을 제안한다. 상태 지문에서 시각·임의 ID·화면 캡처 경로를 제거하되 상품/필터/URL/실행 결과처럼 진행 판단에 필요한 값은 유지한다. 규칙은 파일럿에서 확인하고 held-out 결과를 본 뒤 바꾸지 않는다.

## 파일럿 규모와 평가셋 분리 제안

1. **API 없는 회귀:** 결정적 fake provider와 수동 구성 기억으로 #56 경계를 확인한다. 활성 64개 미만만 쓰는 사례와 64개를 넘는 사례를 구분한다. 중요도·최신성·관련성 순위가 서로 충돌하는 사례를 포함한다.
2. **설계 파일럿:** 개발 과업 1개 × 페르소나 2개 × 정책 3개 × 반복 3회 = **18세션**을 첫 비용 추정 단위로 제안한다. 실제 API를 사용할지는 팀의 예산과 연결 상태에 따라 별도로 실행한다. 이 단계는 효과 확정이나 통계적 충분성의 근거가 아니다.
3. **동결 후 held-out:** 개발에 쓰지 않은 과업 변형 3개 × 페르소나 2개 × 정책 3개 × 반복 5회 = **90세션**을 시간·예산이 허용할 때의 초기 평가안으로 제안한다. 부족하면 사전에 규모를 낮추고 예비 결과로 표시한다. 충분한 검정력은 파일럿 변동·목표 효과·블록 구조를 바탕으로 다시 산정해야 한다.

반복 5회를 기존 `run_comparison(repetitions=1..3)`에 그대로 넣으면 지원되지 않는다. 메모리 전용 실행 계획/manifest를 마련하거나 명시적인 블록별 실행을 기록해야 한다. 기존 파일을 중복 실행하고 하나의 실험인 것처럼 사후 합치지 않는다. [기존 반복 제한](https://github.com/2026-2-1/Persona/blob/2c5f72ad0366b406193f1b382006927ce24c5dbe/src/uxagent/experiments.py#L16)

여기서 개발/held-out 분리는 모델 파인튜닝을 했다는 뜻이 아니다. 프롬프트·가중치·평가기·반복 규칙을 조정하는 데 사용한 과업과 최종 평가 과업을 분리한다. 같은 사이트 템플릿의 상품명만 바꾼 변형은 독립 사이트 일반화 증거가 약하다고 기록한다. 사람 데이터로 파인튜닝한다면 별도로 참가자/세션 단위 분리와 라이선스·동의·중복 검사를 정해야 한다.

보고 시 정책별 원시 세션표와 대응 블록 차이, 성공률의 불확실성, 시간/비용 분포를 제공한다. 3회 반복의 작은 차이를 효과 확정으로 쓰지 않으며, 한 페르소나·한 과업의 반복을 독립 사용자 수로 세지 않는다. 여러 가중치를 시험했다면 실패한 조건도 기록하고 최종 선택과 탐색 결과를 구분한다.

## 팀 공유·논문 작성에 사용할 수 있는 주장

현재 말할 수 있는 것은 “메모리 정책의 비교 실험을 준비했고, 특정 PR에 상한·비동기 중요도·단계 기록 구현이 포함됐다”까지다. fake/mock 통과는 기록·예산·출처 계약 검증으로, 실제 모델 rollout은 정책의 과업 수행 결과로 구분한다.

실험을 수행한 뒤에는 “고정된 과업·모델·예산 범위에서 정책별 성공·반복·시간·비용 차이를 관찰했다”라고 범위를 적을 수 있다. 실제 사람의 행동 분포·판단과 비교하지 않았다면 인간 행동 재현성, 실제 UX 문제 탐지 정확도, 인간 참가자 대체 가능성은 검증되지 않았다고 적는다. 독립 평가기의 과업 성공이 높다는 사실만으로 사람 시뮬레이션 품질을 설명하지 않는다.

다음 회의에서는 연구 질문과 3개 정책, held-out 과업, 예산, 메모리 실험 실행기 담당, #54/#55/#56의 통합 순서를 확정하면 된다. 담당자 배정이나 회의 결정은 이 조사에서 새로 만들지 않았다.
