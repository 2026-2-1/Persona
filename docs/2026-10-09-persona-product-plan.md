# Persona 통합 제품 기획 초안

작성일: 2026-10-09 | 상태: 검토용 제안, 구현 승인 전

> 1차 MVP 구현 현황은 [현재 상태](current-state.md), 실제 검증은 [검증 기록](verification.md)를 따른다. 아래 본문에는 아직 구현되지 않은 장기 제안도 포함된다.

## 1. 제품 목표

사이트와 고객 과업을 입력하면 가정 페르소나 에이전트가 과업을 수행하고, 검증된 결과와 실행 근거를 보여주며, 개발자가 수정 후 같은 조건으로 재검증할 수 있는 개선 카드를 제공한다.

1차 발표에서는 과업 테스트와 일반 AI·페르소나 AI 비교를 각각 대시보드 메뉴에서 열 수 있게 한다. 실제 사용자 행동·만족도·매출 효과를 검증했다고 해석하지 않는다.

근거 자료는 사용자가 제공한 산학협력프로젝트 수행계획서, prototype 브랜치 e4dfa98, 사용자와의 기획 논의다. 계획서의 전체 기술 스택은 최종 목표이며 1주일 MVP에서 모두 전환하지 않는다. 문서에 포함된 개인정보는 이 기획에 전재하지 않는다.

## 2. 화면과 사용자 여정

| 메뉴 | 사용자 목적 | 주요 화면 |
|---|---|---|
| 시작·설정 | 분석 조건을 쉽게 만들기 | 데모, 사이트 URL, API 연결, 대화형 질문, 확정 설정 카드 |
| 과업 테스트 | 수행 결과와 실패 지점을 보기 | 진행 화면, 과업 성공률, 오류·복구, 환경별 결과, 단계별 근거 |
| AI 비교 실험 | 페르소나의 효과를 비교하기 | 일반 AI·페르소나 AI의 대응 실행 비교, 차이, 원자료 |
| 개선 보드 | 무엇을 어떻게 수정할지 판단하기 | 후보·검토·합의·개선·재검증 상태별 문제 카드 |
| 실행 기록 | 판단 근거를 확인하기 | 전후 스크린샷과 URL, 행동, 결과, 모델 호출, 짧은 행동 설명 |

사용 흐름: 데모 또는 내 사이트 선택 → API 연결 → 과업 설명 → 필요한 정보를 한 번에 하나씩 질문 → 과업·성공 조건·페르소나·환경·반복 수·예산 상한 확인 → 실행 → 결과 → 근거 검토 → 개선 카드 → 같은 조건으로 재검증.

설정 대화는 명시적인 설정 카드를 갱신한다. 시작 전 사용자가 성공·중단 조건을 확인한다. 기본 화면에서는 모델 내부 설정을 감추고 고급 설정에서 노출한다. API 키는 채팅, 브라우저 localStorage, 실행 로그, 내보내기에 저장하지 않는다. 1차 로컬 모드에서는 서버 메모리의 세션 연결을 우선하며 재시작 후 재입력한다. 공개 다중 사용자 서비스의 인증·암호화 저장·사용자별 격리는 후속 범위다.

결과 질의응답은 저장된 기록과 카드 ID를 근거로 답하며 실행·단계 링크를 제공한다. 기록으로 알 수 없는 원인과 사용자 감정은 미확인으로 설명한다. 근거가 없는 코드 위치나 원인을 만들어내지 않는다.

## 3. 평가 기준과 점수 표현

1차에는 임의 가중치의 종합 UX 점수를 만들지 않는다. 비율은 원래 비율을 0~100으로 표시하며 분자·분모·조건·반복 횟수를 함께 제공한다. 합성 지표가 필요하면 예비 실행 후 정의와 가중치를 고정하고 버전을 남긴다.

| 지표 | 정의 | 제한 |
|---|---|---|
| 과업 성공률 | 독립 평가기로 성공 확인된 세션 / 사전 등록 평가 세션 | 시간 초과·오류·차단·취소를 분모에 포함; 미실행·미확인도 별도 집계 |
| 수행 효율 | 성공 실행의 행동 수·소요 시간 중앙값 | A/B 행동 수 비교는 양쪽 모두 성공한 대응 실행으로 계산; 전체 종료 사유도 공개 |
| 환경 민감도 | 동일 설정의 환경별 성공률 차이(%p) | 화면 크기·네트워크 등을 한 요소씩 변경; 반복 변동과 구분 |
| 반복 안정성 | 동일 조건 반복의 성공 횟수와 행동 수·시간 분포 | 소수 예비 실행으로 일반화하지 않음 |
| 오류 발생률 | 오류가 발생한 행동 시도 / 전체 행동 시도 | 관찰·모델·실행·네트워크 등 구분 |
| 복구율 | 정해진 복구 가능 오류 사건 중, 3회 이내 후속 행동으로 정의된 정상 상태에 복귀한 사건 / 복구 가능 사건 | 3회는 예비 실험 기본안; 본 실험 전 고정. 회복 후 과업 성공은 별도로 기록 |
| 기록 확보율 | 전후 화면·URL·결과·시각이 완전한 행동 / 전체 시도 행동 | 계획서 목표 95% |
| 문제 후보 정확도 | 실제 문제로 최종 합의된 후보 / 실제 문제와 오탐으로 최종 판정된 후보 | 보류·도구 오류·중복 건수를 별도 공개, 검토 완료율 함께 표시 |
| 검토·근거 연결 | 중복 정리 후보의 2인 검토 완료율, 최종 카드의 근거 연결률 | 계획서 목표 100%; 독립 최초 판정과 합의 판정 보존 |
| 안전 | 사전 정의한 금지 행동 검증의 차단 통과율 | 계획서 목표 100%; 정상 정책 차단은 조작 오류와 구분 |
| 비용 | 전체 호출 비용, 검증 성공 1회당 비용 | 알려지지 않은 비용은 미확인, 성공 0회는 성공당 비용 해당 없음 |

평가 상태는 성공·실패·미확인으로 구분한다. 모델의 완료 선언은 독립 평가 결과와 별도 보존한다. 기록이 없는 항목은 0점이 아닌 측정 전·미확인, 복구 가능 오류가 없는 경우 복구율은 해당 없음으로 표시한다.

첫 화면의 요약은 과업 달성, 환경별 결과, 오류 복구, 근거 완성도다. 신호등 색상만으로 판정을 표현하지 않고 문구와 횟수를 함께 제공한다. 미확인·보류가 있으면 개수를 노출한다.

문제 누락률은 사람이 독립적으로 발견한 참조 목록이 있을 때만 계산한다. 여러 세션에서 반복된 같은 문제를 독립적인 새 문제로 세지 않는다.

## 4. 개발자용 출력 계약

최종 산출물은 실행 요약, 개선 카드 묶음, 원자료, 개선 전후 비교표다. 카드와 내보내기는 동일 데이터를 사용한다.

| 카드 필드 | 내용 |
|---|---|
| 식별·범위 | 카드 ID, 사이트·화면 버전, 과업, 환경, 발생 URL, 영향 조건 |
| 문제 요약 | 사용자 과업을 어떻게 방해하는지 한 문장 |
| 사실·가설 | 실제 관찰 행동과 추정 원인, 대안 설명을 분리 |
| 발생량 | 영향을 받은 세션 / 해당 조건 전체 세션; 중복 정리 기준 |
| 근거 | 실행 ID·단계 ID·관찰 ID, 전후 화면, 행동과 결과 |
| 분류 | UX 후보, 에이전트·도구 오류, 환경 오류, 정상 정책 차단, 판단 보류 |
| 검토 | 두 검토자의 독립 판정, 최종 합의, 근거와 시각 |
| 심각도 | 과업 차단 / 큰 지연·우회 / 경미한 불편; 관찰 근거로 제안 후 사람 확정 |
| 개선 제안 | 변경할 화면·문구·상호작용, 제안 이유와 부작용 가능성 |
| 개발 힌트 | 공개 DOM에서 확인한 요소 단서; 소스 연결 없으면 파일·라인은 알 수 없음 |
| 완료 조건 | 수정 후 관찰 가능한 정상 동작과 회귀 확인 항목 |
| 검증 상태 | 개선 전후 성공률·행동 수·새 문제·비용, 검증 전·완료·불충분 |
| 작업 관리 | 담당자, 상태, 선택적인 작업 크기 추정과 추정 근거 |

우선순위는 과업 영향과 발생 범위로 제안하고 사람이 확정한다. 실행 횟수가 적으면 발생량의 한계를 명시한다. 모델 confidence를 문제의 실제 존재 확률로 표시하지 않는다. 사이트 문제와 자체 에이전트 오류는 서로 다른 작업 목록으로 전달한다.

상태 흐름: AI 후보 → 검토 중 → 2인 검토·합의 → 개선 예정 → 수정됨 → 재검증 완료. 오탐·도구 오류·보류·중복은 삭제하지 않고 별도 상태로 보존한다. 후보 상태에서도 내보낼 수 있으나 미검토 표시를 유지한다.

출력 형태:

- 1차: 대시보드 개선 카드, HTML 요약 보고서, 개발 이슈용 Markdown, CSV/JSON 원자료.
- 2차: A/B 비교 보고서와 오프라인 근거 묶음; 필요하면 PDF 보고서.
- 3차: 검증된 실행·결과 조회·카드 조회를 MCP로 제공; 브라우저 연동은 선택 확장.

외부 이슈 자동 등록은 1차 범위가 아니다. 내보내기에는 키·인증정보가 포함되지 않게 하고 스크린샷과 URL에 민감정보가 포함되었는지 검토할 수 있어야 한다.

## 5. Fast/Slow Loop 적용

UXAgent의 두 루프는 기존 연구에서 가져온 설계 근거다. 현재 prototype에 FastLoop, MemoryStore, SlowLoop가 있으며 Slow Loop와 Wonder는 기본 비활성이다. 현재 구현은 논문 전체 재현이라고 부르지 않는다.

- Fast Loop: 현재 화면 관찰 → 최근 기록 검색 → 다음 행동 제안 → 별도 정책 검사·실행기 → 새 화면 확인.
- Slow Loop: 특정 시점의 기록 snapshot으로 반복·실패를 요약하고 다음 탐색의 초점을 메모리에 추가한다. 브라우저를 직접 변경하지 않는다. 결과에는 근거 시점과 출처를 붙이고 Fast Loop는 다음 판단에서 사용할 수 있다.
- 실행 후 분석: 전체 실행을 대상으로 지표·중복 문제·개선 카드·보고서를 생성한다. 실행 중 Slow Loop와 별도 기능이다.
- 평가기: 행동 제안과 분리해 성공 조건을 확인한다. Slow Loop의 의견으로 성공 판정을 덮어쓰지 않는다.

관찰 사실, 모델이 생성한 가설, 사람 판정을 분리 저장한다. Slow Loop 실패가 Fast Loop를 중단하지 않도록 상태를 기록한다. 공통 비용·요청 예산을 적용한다. 1차는 기존 Fast Loop를 기본으로 사용하고, Slow Loop는 2차에서 on/off 비교한다. Wonder는 초기 비교에서 비활성으로 유지한다.

## 6. 비교 실험

페르소나 유무를 비교할 때는 같은 구매 제약·모델·프롬프트 구조·과업·화면·환경·호출 상한·반복 수를 유지하고 배경·탐색 성향만 변경한다. 실행 순서를 섞고 새 브라우저 context를 사용한다. 성과는 성공률·효율·사람 인정 문제 수·오탐·비용으로 구분한다.

대표 과업 1개, 페르소나 2종, 조건별 3회 반복의 1차 제안은 2개의 대응 블록 × 2개 AI 조건 × 3회 = 12세션이다. 일반 AI 조건은 대응하는 구매 제약을 유지한다. 예비 실행으로 세션당 비용을 먼저 측정하고 예산 내에서 사전에 반복 수를 결정한다. 작은 표본의 비교는 예비 결과로 표시한다.

Jev 실험은 직접 행동 생성 / 같은 모델의 후보 선택 / Jev 후보 선택+fallback / Jev 강제 선택을 구분한다. 동일 후보를 사용해 후보 제한 효과와 모델 효과를 분리한다. 현재 후보 생성의 옵션 ID 충돌, 과업 전체를 입력값으로 사용하는 방식, 완료 후보 부재를 먼저 확인·정리한다. 계획서의 Jev 문제 후보 분류 역할은 다음 행동 선택과 별도 실험이다.

## 7. 단계별 범위와 4명 협업

| 단계 | 결과 | 완료 확인 |
|---|---|---|
| 1차, 10/16 최소 시연 목표 | 대표 과업 1개, 페르소나 2종, 환경 1개; 테스트·AI 비교 메뉴; 설정·키 연결·실행·근거·카드·내보내기 | 완료 선언이 아닌 평가기 판정, 성공·실패 기록 조회, 비교 조건 확인, 민감정보 없는 출력 |
| 2차 | 4개 과업과 환경 비교, 사람 검토, 기술별 독립 실험, 재현 화면 A/B | 개선안 1개 이상 비교, 새 문제와 비용 포함; 기술 효과 없거나 불확실해도 결과 보존 |
| 3차 | 논문·기술백서·기업 검토용 개선 코드·재현 자료, 선택 MCP·브라우저 연동 | 계획서의 12/4 검증, 12/11 보고 일정 기준으로 우선순위 관리 |

1차 일정: 1일차 과업·평가·기록 계약; 2~3일차 실행·평가기·기록; 3~5일차 화면·키 연결·비교·출력; 6일차 통합·실패 검증; 7일차 시연·발표. 핵심 흐름이 통과한 후 환경 1개를 추가한다.

| 역할 | 공통 기반 | 2차 실험 |
|---|---|---|
| A | 대시보드·대화형 설정·개선 보드 | 초보자의 설정 시간·오류·결과 이해도 개선 |
| B | 브라우저·행동 실행·복구 | Jev 후보 폭·fallback, Fast/Slow on/off |
| C | 요구사항·과업·평가기·2인 검토 운영 | MiroFish 페르소나 보조의 현실성·유용성 |
| D | 로그·지표·내보내기·비교 | 프롬프트 개선, 데이터 확보 후 파인튜닝 타당성 |

실험마다 가설·주 지표·회귀 지표·시간/비용 상한을 구현 전에 기록한다. 기능별 on/off와 설정 버전을 보존한다. 파인튜닝은 검토된 데이터와 분리된 평가 과업이 준비되었을 때 진행한다. MiroFish 전체 시뮬레이션을 기본 실행기에 강제로 결합하지 않는다. 효과가 확인되지 않으면 통합하지 않을 수 있고, 소수 표본의 불확실성을 효과 없음으로 단정하지 않는다.

## 8. 기존 문제와 회귀 방지

기존 테스트에는 설정 이동 후 persona 경로, 생성 후 과거 실행 혼입, 최신 관찰·중첩 실행 표시, 실행 실패 전달, API 키 노출 방지, stale observation 차단, 예산 종료, 잘못된 완료 주장 구분 검사가 있다. 관련 부분을 변경할 때 해당 검사를 유지한다.

현재 외부 사이트 evaluator는 미확인이며 범용 성공 검증을 제공하지 않는다. 현재 설문·인터뷰는 로그 기반 템플릿이다. 이 초안의 대화형 설정·결과 Q&A·개선 보드·일반 AI 비교·보고서 계약은 새로 개발할 범위다. 기존 실행기를 유지하고 UI/API 경계를 필요한 만큼 추가한다. 전체 큐·DB·스토리지 전환은 후속 단계로 둔다.

작업마다 docs에 설계 결정과 문제·원인·해결·검증·함께 발생한 회귀를 기록하고 README를 갱신한다. .env·API 키·인증정보는 push하지 않는다.

## 9. 연구 활용과 출처

논문에서 설명한 아키텍처·방법을 이해하고 독립적으로 구현하는 것과 원문 코드·문장·그림을 복제하는 것은 구분한다. 아이디어와 표현의 구분은 한국저작권위원회 안내를 참고한다. 특허·계약 등 별도 권리까지 이 문서가 확인한 것은 아니다.

UXAgent 공식 저장소 README는 MIT License를 명시한다. 실제 코드 재사용 전 대상 버전의 라이선스·저작권 고지와 별도 자료·의존성 조건을 확인하고, MIT 적용 코드의 배포에는 저작권·허가 고지를 포함한다. 논문의 arXiv 표시 라이선스는 arXiv 배포용 비독점 라이선스이며 제3자의 그림·본문 자유 재사용 허락과 같지 않다. 사용자가 첨부한 이미지의 제작자·이용허락은 확인되지 않았다.

발표·논문에서는 두 루프 자체를 자체 신규 발명으로 주장하지 않는다. UXAgent를 직접 인용하고, 실제 읽고 적용한 Park et al. 연구 및 이중처리이론 문헌을 인용한다. 기여는 과업별 성공 검증, 실행 근거와 사람 검토의 연결, 환경·복구 분석, 개발자 카드와 개선 전후 비교로 구체화하고 실제 검증 범위만 주장한다.

## 10. 세부 기능 점검과 쉬운 계정 연결 (추가 제안)

클릭 횟수는 조작 기록 중 하나다. 검색·필터·정렬·상품 정보·수령 안내의 정상 동작을 기능별 사전 정의한 기대 결과로 확인한다. 결과는 기능 동작 검증, 사용성 후보, 도구 미지원·판정 불가로 구분한다.

| 기능 | 점검 사례 | 검증할 결과 |
|---|---|---|
| 검색 | 정상 키워드, 결과 없음, 검색어 변경, Enter 제출 | 입력 검색어·URL·결과 제목/상품·빈 결과 안내의 대응 |
| 필터 | 가격·사이즈·용도 조합, 해제, 전체 초기화 | 선택 상태·결과 조건·결과 수·초기화 상태의 일치 |
| 정렬 | 가격순 변경 | 실제 표시 가격의 순서; 할인·변형 가격은 정의된 규칙 적용 |
| 상품 상세 | 사이즈·용도·재고·수령 정보 확인 | 필수 정보 존재·표시 가능·선택 상태와 안내의 대응 |
| 상호작용 | 메뉴·모달·키보드·뒤로가기 | 표시·닫힘·포커스·상태 유지의 정의된 조건 |
| 반응형 | 화면 크기 변경 | 잘림·겹침·조작 가능성, 주요 정보 접근 |
| 오류와 복구 | 재현 화면의 지연·실패·빈 결과 | 안내·재시도·복귀·입력 보존; 운영 사이트 장애를 임의 유발하지 않음 |

OpenAI는 과업 분해, 실제 검색어/입력값 생성, DOM과 필요시 스크린샷 해석, 다음 행동 제안, 근거 기반 요약에 사용한다. 조작은 기존 Playwright 실행기로 제한하고 가격·정렬·선택 상태 등 명확한 조건은 코드 평가기로 판정한다. 관련성·정보 이해도 등 해석이 필요한 판정은 AI 제안과 사람 검토를 구분한다. API 교체만으로 iframe·canvas·custom control 지원이나 전체 사이트 검증이 해결되지는 않는다.

기능 계약은 시작 상태, 입력값, 허용 행동, 기대 결과, 성공·중단 조건, 관찰 근거를 포함한다. 1차에는 검색 정상 입력·빈 결과·필터 적용/해제·상품 정보 확인을 대표 시나리오의 하위 점검으로 구현하고, 나머지는 후속 범위다. 검색 정상 입력은 과제 문장 전체가 아닌 목적에 맞는 실제 검색어를 생성한다. 더 넓은 탐색에는 새 scroll·keypress·custom control 관찰 계약과 회귀 검증이 필요하다.

대시보드 기능별 결과 표는 통과·실패·미확인·미지원 및 근거를 제공한다. 예정·시도·판정 완료 점검 수를 각각 표시한다. 전체 사이트가 점검됐다고 표시하지 않으며 미지원 항목을 분모에서 조용히 제거하지 않는다. 개선 카드는 검색·필터 등 기능과 연결한다. 구체적 정답 데이터가 없는 상품 검색의 의미적 관련성은 완전한 정답으로 단정하지 않는다.

2026-10-09 공식 문서에서 Sign in with ChatGPT의 선택적인 구독 사용 권한을 확인했다. 적격 Plus·Pro 사용자가 오픈소스·로컬 앱에서 적격 AI 요청을 기존 한도로 수행하는 연결을 검토한다. 로그인만으로 모델 호출 권한이 생기지는 않는다. 유료·원격 호스팅 서비스는 별도 접근 신청 조건이 있으므로 공개 서비스 지원을 약속하지 않는다.

연결 UI는 데모 체험 / ChatGPT로 연결(해당 배포의 지원 확인 후 제공) / API 키로 연결이다. ChatGPT 연결은 브라우저 로그인 → 구독 사용 동의 → 실제 반환 권한 확인 → 연결 시험 → 구독 사용 중과 사용량 관리 링크 표시 순서다. 부적격·동의 거절·한도 도달 시 이유를 설명하고 사용자가 다른 경로를 선택하도록 한다. API 요금제로 자동 전환하거나 키·토큰을 프런트엔드에 노출하지 않는다. 구독 경로는 원화 비용 대신 구독 한도 사용과 측정 가능한 호출·토큰을 표시한다.

현재 OpenAI 연동은 Chat Completions 기반이므로 OAuth 토큰을 그대로 끼우는 방식이 아니다. 구독 연동에는 적격 Responses API 요청과 스트리밍 등 preview 계약을 따르는 별도 provider가 필요하다. 사용 가능한 모델·도구는 연결 후 확인한다. 구독 연결 도입 여부는 로컬 검증으로 판단하며 이 문서는 지원을 검증한 결과가 아니다. 일반 AI·페르소나 AI 비교에는 동일 연결 경로·동일 모델을 사용한다.
