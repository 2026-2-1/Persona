# PR과 리뷰 규칙

## 제목과 본문

제목은 `type: 변경 결과` 또는 `type(scope): 변경 결과`로 쓴다. 예: `feat(review): 사람 판정 저장과 조회 추가`. 기존 열린 PR 제목을 소급해서 실패 처리하는 자동 제목 검사는 두지 않는다.

본문에는 다음을 남긴다.

1. 어떤 상황에서 문제가 생겼고 변경 후 어떻게 동작하는지.
2. 관련 이슈와 변경 범위, 실제 검증 명령·결과.
3. 화면 변경이면 전후 화면, 연구 변경이면 기준 버전·조건·지표·한계.
4. 남은 제한과 다른 역할이 확인할 입출력 변경.

부모 이슈의 일부만 구현하면 `관련: #번호`로 연결한다. 전체 완료 조건을 충족한 이슈만 종료 대상으로 표시한다. prototype은 기본 브랜치가 아니므로 `Closes #번호`만으로 즉시 자동 종료된다고 가정하지 말고 병합 후 이슈 상태를 확인한다.

## 리뷰 요청과 승인

준비 중에는 Draft PR을 사용하고, 검토할 수 있을 때 Ready for review로 전환한다. **작성자 외 쓰기 권한이 있는 팀원 1명 이상을 Reviewers에 지정**한다. 기본은 PR 작성자가 변경 내용을 이해할 수 있는 팀원을 선택하는 방식이다. 담당자와 리뷰어는 다르며 Assignees 지정만으로 리뷰 요청을 대신하지 않는다.

리뷰어는 단순 댓글이 아니라 GitHub의 **Approve** 또는 **Request changes**로 검토 결과를 남긴다. 작성자 본인과 AI 검토 결과는 필수 사람 승인 1명을 대체하지 않는다. 작업을 함께 수정한 사람 외의 검토도 가능하면 포함한다.

리뷰 확인 항목:

- 이슈의 완료 조건과 실제 동작이 맞는가?
- 관찰 사실·AI 판단·독립 판정·사람 검토를 혼동하지 않는가?
- 정상·실패·미확인·중지와 관련 회귀가 검증됐는가?
- 공통 필드 변경이 소비 모듈·화면·내보내기에도 반영됐는가?
- 불필요한 파일·키·원자료가 포함되지 않았는가?

검토 의견은 `필수 수정`, `질문`, `제안`을 구분한다. 작성자가 대응 내용을 남기고 확인된 대화를 해결한다. 새 변경으로 기존 승인이 취소되면 다시 검토를 요청한다.

GitHub의 필수 승인 규칙은 병합 전 승인 인원을 강제한다. 검토 전 Reviewers 선택 자체는 이 문서와 PR 체크리스트로 운영하며, 자동 지정은 별도 도입할 수 있다.

## 병합 기준

- main·prototype: 작성자 외 승인 1개, 오래된 승인 취소, 리뷰 대화 해결, 관리자도 규칙 적용, force push·브랜치 삭제 금지.
- prototype: `check (ubuntu-latest, 3.11)`과 `check (windows-latest, 3.13)` 성공, 대상 브랜치 최신 변경 반영.
- main: 현재 초기 골격과 prototype의 CI가 다르므로 이번 설정에서는 특정 CI 이름을 필수로 고정하지 않는다. prototype 통합 PR에서 실행된 검사와 시연 결과를 리뷰하고, 통합 후 실제 CI 이름에 맞춰 필수 검사를 추가한다.
- 규칙 변경은 GitHub 서버 설정이다. 문서나 JSON을 병합하는 것만으로 서버 설정이 자동 적용되지는 않는다.

원격에 적용한 값과 재확인 방법은 [브랜치 보호 설정](branch-protection.md)에 기록한다.
