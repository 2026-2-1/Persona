# D 파트 진행 현황과 프로토타입 회의 안건

기준일: 2026-10-14, 한국 시간. 대상: Persona 개발팀. D 담당: 곽태훈.

**D-01~D-04는 작업 브랜치에서 구현·로컬 검증을 완료했다. prototype 통합과 팀원 리뷰는 남아 있으며, D-05는 아직 완료하지 않았다.** 이번 회의에서는 10/18 시연 범위, 선행 PR 통합 순서, 추가 수정 우선순위와 검증 담당을 결정한다. 아래 일정·담당 제안은 회의 확정 사항이 아니다.

현재 실행기는 Python/Playwright이며 UI는 기존 정적 대시보드를 확장했다. C의 검토 저장 API와 집계를 재사용했다. 별도 DB나 프런트 프레임워크 교체는 하지 않았다.

### 검증 수치의 의미

| 시점 | 당시 전체 pytest | 주요 브라우저 검증 |
|---|---:|---|
| D-01 | 269 통과 | 입력·저장 관련 12개 |
| D-02 | 276 통과 | 기존 12개 + 초안/경합 7개 |
| D-03 | 281 통과 | 검토 관련 24개 |
| D-04 최종 | 286 통과 | 신규 비교 5개, 기존 링크 회귀 포함 집중 6개 |

위 수치는 각 시점의 누적 회귀 검사 개수이며 합산하지 않는다. D-04 최초 전체 검사에서 없는 실행 버튼에 이동 ID가 남은 문제를 발견했고, 제거한 뒤 286개를 통과했다. doctor와 무료 Mock 실행도 성공했다. 자세한 실행 기록은 [verification.md](../verification.md)에 있다.

### 시연에서 보여줄 수 있는 것과 아직 주장할 수 없는 것

- 보여줄 수 있음: 실행 근거를 열어 후보를 검토하고 저장한 뒤 이력을 다시 확인하는 흐름, 자동 갱신 중 입력 유지, 측정 누락을 숨기지 않는 비교표.
- 표시 검증 예시: 성공 2/예정 5=40%, 전체 비용 미확인·측정 부분값 $0.125, 전체 기록 확보율 미확인·측정 범위 3/4행동=75%. 이 수치는 **가상 UI 검증 표본**이다.
- 아직 검증하지 않음: 실제 유료 모델 간 성능 우열, 인간 행동·판단 재현, 실제 사이트 전체 UX 평가, 독립 2인 합의.
- 미저장 초안은 페이지 메모리에만 있다. 전체 새로고침·탭 종료 후 복원되지 않는다. 저장된 판정은 서버에 남는다.
- 검토자 별칭은 인증 신원이 아니다. 유효 후보 판정은 과업 성공이나 확정 UX 결함을 뜻하지 않는다.

## 2. PR 상태와 통합 순서

2026-10-14 GitHub 조회 기준이다. CI 결과는 해당 PR에 표시된 결과이며 다른 브랜치와 합친 결과를 보증하지 않는다.

| PR | 현재 상태 | 현재 대상 브랜치 | 표시된 원격 검사 |
|---|---|---|---|
| [C #30](https://github.com/2026-2-1/Persona/pull/30) | Open, 리뷰 필요 | prototype | Ubuntu·Windows 성공 |
| [D-01 #37](https://github.com/2026-2-1/Persona/pull/37) | Draft, 미병합 | feat/27-c-review-data | Ubuntu·Windows 성공 |
| [D-02 #38](https://github.com/2026-2-1/Persona/pull/38) | Draft, 미병합 | feat/32-candidate-review | Ubuntu·Windows 성공 |
| [D-03 #49](https://github.com/2026-2-1/Persona/pull/49) | Draft, 미병합 | feat/33-review-draft-retention | Ubuntu·Windows 성공 (2c42f67) |
| [D-04 #50](https://github.com/2026-2-1/Persona/pull/50) | Draft, 미병합 | codex/34-review-history-provenance | Ubuntu·Windows 성공 (f618818) |
| [Brain #48](https://github.com/2026-2-1/Persona/pull/48) | Open, 리뷰 필요 | prototype | Ubuntu·Windows 성공 |

D 기능의 의존 순서는 **#30 → #37 → #38 → #49 → #50**이다. 선행 기능 브랜치를 대상으로 둔 것은 D 변경만 검토하기 위한 것이며, 그 브랜치에 직접 병합하는 절차가 아니다.

통합 시에는 선행 PR을 prototype에 반영한 다음, 다음 PR의 base를 prototype으로 변경하고 차이를 다시 확인한다. 선행 변경이 중복 표시되거나 충돌하면 별도 통합 커밋으로 정리한다. Git 이력 방식에 따라 재정리가 필요할 수 있으므로 base 변경만으로 항상 해결된다고 가정하지 않는다. 각 단계에서 최신 CI와 작성자 외 1명 승인을 확인한다. PR 작성자가 리뷰어를 선택한다.

**CI 자동 실행 조건 수정 반영:** 2026-10-14 D-03과 D-04 브랜치에 codex/** push 지원을 추가했다. 기존 push 대상과 prototype/main PR 검사는 유지한다. 선행 기능 브랜치 대상 PR도 head 브랜치 push로 검사된다. [워크플로](../../.github/workflows/prototype-ci.yml)의 변경은 prototype에 통합되기 전이므로 다른 미반영 브랜치에도 자동 적용된 것으로 보지 않는다. 실제 자동 실행 결과: [D-03 검사](https://github.com/2026-2-1/Persona/actions/runs/38571360128)는 Ubuntu·Windows 각각 281개, [D-04 검사](https://github.com/2026-2-1/Persona/actions/runs/38571422499)는 각각 286개 테스트를 통과했다. 두 실행 모두 환경 검사와 Mock 실행도 성공했다.

Brain #48은 기록 스키마와 메모리 호환 기반이다. 단계별 Brain 기록의 실제 생성과 대시보드 연결 전체가 구현된 것은 아니다. D 코드와 합친 상태의 호환 검증은 D-05에 포함할지 결정한다.

## 3. 남은 D-05 완료 기준

작업: [#36 검토·비교 화면 통합 시연 및 회귀 검증](https://github.com/2026-2-1/Persona/issues/36). 기존 추정은 개발·검증 2~3시간이며, 충돌 해결·팀원 리뷰·실환경 준비 시간은 별도다. 목표 일정은 10/16~17이다.

| 확인 흐름 | 통과 기준 | 남길 자료 |
|---|---|---|
| 후보 → 근거 → 판정 → 재조회 | 같은 실행·카드·근거 버전으로 저장되고 새로고침 후 조회됨 | 재현 명령·실행 ID·화면 |
| 화면 → 내보내기 | JSON/CSV/Markdown/HTML의 동일 카드 최신 판정이 화면과 일치함 | 형식별 확인 표 |
| 정상·실패·중지·빈 결과·누락 | 상태를 혼동하지 않고 근거가 없으면 명시함 | 시나리오별 기대값/실제값 |
| 작은 화면·자동 갱신 | 입력·버튼 접근 가능, 초안 보존, 표 내부 스크롤 가능 | 화면 크기·조작 절차 |
| 다른 팀원 재현 | 공유한 커밋과 절차만으로 저장·조회·비교 흐름을 재현함 | 재현자·OS·커밋·결과 |
| prototype 통합 | 확정된 통합 커밋에서 필수 CI와 위 시연을 통과함 | 커밋·CI 링크·승인 |

기존 개별 테스트 통과만으로 D-05를 완료 처리하지 않는다. D-05는 전체 프로젝트 통합을 D 혼자 맡는 작업도 아니다. 실행 데이터·API 계약·평가 의미는 각 파트가 함께 확인한다.

### 팀원이 따라 할 시연 순서

1. 회의에서 정한 통합 커밋을 받고 [개발 환경 안내](../development.md)로 환경 검사와 대시보드를 실행한다. 통합 전 미리 확인하려면 D-04 브랜치 `codex/35-comparison-coverage`의 기능 기준 커밋 `4d62f15`를 사용하고 prototype 결과와 구분한다.
2. 무료 합성 시나리오에서 정상 실행과 필터 결함 실행을 만든다. 예: `.venv/bin/python -m uxagent scenario --config configs/scenarios/decathlon-flow.json --defect filter`. Windows 실행 경로는 개발 환경 안내를 따른다.
3. 개선 보드에서 후보의 행동 근거를 연다. 테스트 별칭과 테스트 목적을 적은 메모로 보류 판정을 저장한다.
4. 다른 실행을 왕복하고 페이지를 새로고침한다. 저장된 판정·이력은 유지되고, 새로고침 전 미저장 초안은 사라지는지 구분한다.
5. 판정을 추가해 현재 버전 이력과 최신 판정을 확인한다. 이전 버전 검증은 별도 가상 표본으로 수행해 원본 시연 데이터를 임의 수정하지 않는다.
6. 네 형식으로 내보내 동일 카드 ID·버전·판정·메모를 대조한다. 이 단계는 D-05에서 통합 검증해야 한다.
7. 비교표에서 성공/예정, 실제0/미확인, 부분 측정값을 설명한다. 가상 표본 자동 검사는 `.venv/bin/python -m pytest -q tests/test_comparison_browser.py`로 재현한다. 이전 로컬 8766 미리보기는 공유 환경에 자동 제공되지 않는다.

## 4. 추가 수정 후보와 우선순위

아래는 추가 이슈로 등록하거나 기존 이슈의 체크리스트에 반영할 후보다. 아직 새 이슈를 등록하거나 담당·기한을 확정하지 않았다.

| 우선순위 | 확인된 문제와 근거 | 제안하는 완료 조건 | 연결할 작업 |
|---|---|---|---|
| 수정 반영 후 통합 필요 | codex/** CI 자동 실행 조건을 D-03/D-04에 반영함 | 각 브랜치의 원격 결과와 prototype 통합 후 필수 검사를 확인 | 협업 설정 [#31](https://github.com/2026-2-1/Persona/pull/31), D-05 |
| 높음 | `app.js`의 일부 상세/비교 조회 실패가 무시되고 이전 결과를 유지한 채 연결됨으로 표시될 수 있음 | 마지막 성공 갱신 시각·갱신 실패 표시, 오래된 결과임을 안내, 재시도 후 정상 복원 | [#7](https://github.com/2026-2-1/Persona/issues/7) 아래 작은 수정 이슈 |

D-04는 비교표 범위만 수정했다. 추가 후보 중 CI 외 항목의 구현 규모와 전체 영향은 별도 실패 재현 후 확정한다. 브랜치 간 통합 문제와 사용자에게 잘못된 의미를 전달하는 표시를 먼저 처리하고, 새 그래프·종합 UX 점수는 이번 마감의 필수 범위에 넣지 않는 안을 제안한다.

| 멘토 피드백 | 먼저 프로토타입과 한계를 보여드린 뒤 제공 가능한 실무 자료를 질문 | 시연 자료 담당, 질문 목록, 공유 가능한 자료 범위 |

역할 배정은 A 남규민, B 김재민, C 김태희, D 곽태훈을 유지한다. 위 협업 표는 기존 역할 안에서의 검증 분담 제안이다. 추가 AI 실험 참여는 기본 시연 범위를 확보한 뒤 별도 Issue로 정한다.

AI의 `plan_review`는 사람 후보 검토와 분리한다. 관찰 사실·AI 생성·행동 실행·독립 과업 평가·사람 검토를 같은 판정으로 합치지 않는다. LLM 판단과 인간 판단의 일치 여부는 공개 논문/데이터셋 검토 및 별도 평가가 필요한 후속 연구이며, 파인튜닝 성능을 현재 UI 검증으로 주장하지 않는다.

### 10/18까지의 일정 제안

| 시점 | 목표 | 완료 확인 |
|---|---|---|
| 10/15 | 최소 시연 범위·CI 방침·리뷰어 확정, 선행 PR 순차 통합 시작 | 결정표와 PR 체크 결과 |
| 10/16 | D-05 시연·내보내기 일치, 우선 수정 후보 처리 | 시나리오별 통과/실패 기록 |
| 10/17 | 다른 팀원 재현, prototype 최종 회귀, 시연 자료 준비 | 확정 커밋·CI·재현자 확인 |
| 10/18 | 확정 커밋으로 시연, 한계·후속 실험 설명 | 시연 버전과 미완료 목록 |

리뷰나 통합이 지연되면 Brain 신규 UI 등 선택 기능을 이월하는 방안을 먼저 논의한다. 검증을 생략한 상태를 완료로 표시하지 않는다.
